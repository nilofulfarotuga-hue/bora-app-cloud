## 2. Cenários empíricos analisados

### Cenário (a) — admin tenta fazer **login fresh** como cliente
1. Admin escreve email+password em `ClientLoginScreen`
2. Chama `authStore.loginClientAsync(email, password)` (`client_login_screen.dart:245`)
3. `loginClientAsync` faz signOut prévio (L527-530)
4. `signInWithPassword` retorna user com `meta['bora_role']='admin'`
5. **L545:** `if (metaRole != null && metaRole != 'client')` → true → `await signOut(); return false;`
6. UI mostra erro "credenciais inválidas" ou snackbar similar
7. **Resultado: admin BLOQUEADO da app cliente após signout.**

### Cenário (b) — admin usa a app como cliente com sessão actual
- A sessão actual do admin (`last_sign_in = 2026-04-28 17:53`) foi obtida antes da Fase 1 ter aplicado o trigger ou via Studio. **Refresh tokens mantêm-na viva sem chamar `loginClientAsync`** → não há check de role no refresh path.
- `_handleSession` é chamado no refresh, mas o switch cai no `default: break` (item #2). Nenhum erro, mas `_currentClient` fica `null`.
- **Implicação:** estados em memória podem estar inconsistentes (ex. nome do utilizador não aparece em alguns ecrãs porque `_currentClient` é null) — minor UX bug.
- **Crítico:** se o app fizer signOut por qualquer razão (clear cache, password change, "Sair"), o Danilo cai no Cenário (a) e fica trancado.

### Cenário (c) — admin acede a `/admin`
- `profile_screen.dart:421-422` tem o gate por email → mostra botão.
- `admin_dashboard_screen._isAuthorized` também por email → permite render.
- ✅ Funciona com sessão activa.
- ❌ Inacessível se signout (não consegue ir até ao profile_screen).

## 3. Como o admin chegou ao estado actual

`auth.users.last_sign_in_at = 2026-04-28 17:53:17.85+00` indica que houve um signin verdadeiro **depois da Fase 1**. As únicas formas de isso ter acontecido:

- **Hipótese provável:** signin foi feito antes do `bora_role='admin'` ter sido reaplicado pela Fase 1 (a migration `20260428000001_admin_overrides.sql` re-set o role a 17:??), e `last_sign_in_at` é apenas refresh.
  - Ou: o login foi feito via Studio admin, ou pelo Service Role (que bypass-a tudo).
- **Confirmação a fazer:** próximo signout do Danilo seria fatal. NÃO fazer signout até resolvermos.

## 4. Decisão necessária — 3 opções

### Opção S1 — Aceitar `'admin'` como super-set nos 3 logins (mínima)

Trocar 3 condições no `auth_store.dart`:

```dart
// L545: loginClientAsync
- if (metaRole != null && metaRole != 'client') {
+ if (metaRole != null && metaRole != 'client' && metaRole != 'admin') {

// L711: loginDriverAsync
- if (role != 'driver') {
+ if (role != 'driver' && role != 'admin') {

// L987: loginPartnerAsync
- if ((meta[_kRole] as String?) != 'partner') return false;
+ final r = meta[_kRole] as String?;
+ if (r != 'partner' && r != 'admin') return false;
```

**Trade-off:**
- ✅ Mínima (3 linhas)
- ✅ Semanticamente alinha com "admin tem poder total" (admin pode operar como cliente, driver, partner)
- 🟡 Não toca em server-side (Fase 1 e 2A continuam a funcionar)
- ⚠️ Continua a misturar role admin com role da app — feio conceptualmente

### Opção S2 — Reverter `bora_role` para `'client'` e usar **só** `app_metadata.role='admin'` (mais limpa)

Plano:
1. Migration: `UPDATE auth.users SET raw_user_meta_data = raw_user_meta_data || '{"bora_role":"client"}'::jsonb WHERE email='nilofulfarotuga@gmail.com';`
2. Manter `raw_app_meta_data.role='admin'` (já existe!)
3. Adaptar trigger Fase 1 — passa a proteger `raw_app_meta_data.role` em vez de `bora_role`
4. Adaptar `_admin_op_guard()` — usar `auth.jwt() -> 'app_metadata' ->> 'role' = 'admin'` em vez de `user_metadata.bora_role`
5. Adaptar RLS `admin_audit_log_select_admin` — mesmo padrão
6. Adaptar storage policy `admin_read_all_driver_docs` — mesmo padrão
7. Helper Dart `AuthService.isAdmin()` lê `appMetadata['role'] == 'admin'`

**Trade-off:**
- ✅ Mais segura: `app_metadata` é imutável pelo cliente (só service_role escreve)
- ✅ Separa conceitualmente role da app de role admin
- ✅ Admin user volta a ser cliente normal (login funciona)
- ❌ Migration mais complexa (RPCs + RLS + trigger + Dart)
- ❌ Mais superfície a tocar antes do lançamento

### Opção S3 — Adicionar claim separada `bora_admin: true` ortogonal

Plano: manter `bora_role='client'` e adicionar `bora_admin: true` em paralelo no `raw_user_meta_data`.

**Trade-off:**
- ✅ Admin pode ter qualquer role da app
- ❌ 2 fontes de truth no mesmo bucket (claim duplicada)
- ❌ Mais campos a manter — não há ganho real sobre S2

## 5. Recomendação

**Opção S2** (usar `app_metadata.role='admin'`).

Justificação:
1. **Já está lá.** O admin user **já tem** `raw_app_meta_data.role='admin'` (descoberto na B.1.4). Não precisamos criar nada — só usar a claim que já existe.
2. **Mais segura.** `app_metadata` só pode ser escrito pelo service_role (não pelo cliente, mesmo via `auth.updateUser`). Imune a ataques de escalation via signup.
3. **Faz a Fase 1 mais robusta.** O trigger anti-overwrite torna-se redundante (porque o cliente nem consegue escrever a claim). Podemos manter o trigger por defesa em camadas, mas com peso menor.
4. **Resolve a regressão.** Reverter `bora_role` para `'client'` no admin user faz com que `loginClientAsync` aceite o login, e a app cliente volta a funcionar para o Danilo.
5. **Limpa o conceito.** `bora_role` é da app (client/driver/partner), `app_metadata.role` é admin (independente).

**Riscos da S2:**
- O `app_metadata.role` actual contém `"role": "admin"` — mas Supabase também usa `app_metadata.role` para outros fins (ex: ldap)? Não — em Supabase puro, `app_metadata` é livre, e `role` no JWT root vem de `aud`, não daqui. **Sem conflito conhecido.**
- Migrations de DB (RLS + trigger + `_admin_op_guard`) requerem coordenação. Mas o trabalho já feito na Fase 1 e 2A assenta numa estrutura modular — alterar 1 função guard alimenta tudo.
